# Auto-merge — single pass

This skill performs ONE unattended pass over the open PRs and then exits. It does NOT loop, schedule, or re-arm itself — cadence is handled externally (e.g. `/loop 15m /auto-merge`). It runs non-interactively: there is NO user to respond, so NEVER use the AskUserQuestion tool or any interactive prompt — it will stall the run. Make every decision autonomously. When a human decision is genuinely needed, do NOT ask: tag @acksell in a PR comment (subject to the idempotency guard below) and hold/skip that PR rather than merging. When uncertain, default to NOT merging.

Task: Scan open PR's and check if the review process is complete and the PR can be merged to main. https://github.com/Acksell/clank/pulls. Don't attempt to resolve merge conflicts (skip any PR that has them). Skip draft PR's entirely. The review process is complete when all the AI-review bots' comments are addressed by the user, and there are no on-going status checks. The PR should have been inactive for at least 15 minutes before auto-merging is allowed, and all status checks must be green.

HARD STOP — a green status check is NOT proof that a review happened. Bots can report a SUCCESS/green check while skipping the actual review (e.g. rate-limited: "review limit reached", "couldn't start this review"). So "all checks green" is necessary but NOT sufficient. Before merging, require positive evidence that a TRUSTED AI reviewer actually COMPLETED a substantive review of the CURRENT HEAD commit. The trusted reviewers are Greptile and Gemini Code Assist — at least ONE of them must have a completed review of the current HEAD (see next paragraph). Treat any reviewer whose comment/check says it was rate-limited / couldn't start / errored as "did not review" (it does not count toward this requirement), regardless of its check status. GitHub Copilot also auto-reviews these PRs (its review posts under the login `copilot-pull-request-reviewer`), but it is NOT trusted on its own — its review is welcome as extra signal yet NEVER satisfies this requirement by itself, so never merge on Copilot alone.

Completed-review proof — at least ONE of these must hold on the PR's current HEAD:
- Greptile: its confidence score lives in the PR description/body (NOT in comments or reviews) — inside the `<!-- greptile_comment -->` block as a header "Confidence Score: X/5", with a footer "Last reviewed commit: …". Read it with `gh pr view <n> --json body`. Greptile satisfies the gate only if that block is PRESENT, its "Last reviewed commit" equals the current HEAD, AND the score reads exactly "Confidence Score: 5/5" (anything lower fails). NOTE: Greptile frequently exhausts its monthly cap (~50 PRs/month) and will simply be ABSENT — that is expected; fall through to Gemini rather than tagging @acksell just because Greptile is missing.
- Gemini Code Assist: a substantive code review it posted against the current HEAD satisfies the gate. Identify it by its review author login `gemini-code-assist` (verified) — read `gh api repos/<o>/<r>/pulls/<n>/reviews` (or `gh pr view <n> --json reviews`); its review body opens with `## Code Review`. IMPORTANT: Gemini emits **NO status check of any kind** — do not wait for, or expect, a Gemini check; detect it ONLY by its submitted review. Confirm it actually produced a real review (a summary + findings, not an error or "unable to review" message) and that the review's `commit_id` matches the current HEAD SHA (proving it reviewed the latest code, not a stale push). Gemini publishes no numeric score, so the quality bar is the standing rule above that all of its comments are addressed. (Other bot logins on this repo: `greptile-apps`, `coderabbitai`, `cubic-dev-ai`, `copilot-pull-request-reviewer`.)
If NEITHER Greptile nor Gemini has a completed review of the current HEAD, do NOT merge — tag @acksell instead (subject to idempotency).

Exercise your own risk-judgement. If a human is needed, tag @acksell in a PR comment. Idempotency: before tagging, fetch existing PR comments and skip posting if an earlier pass already left its tag (HTML marker `<!-- automerge:... -->`) and there has been no new activity (commit/comment) since it was posted; otherwise just report status. When merging, squash-merge to match the repo's "(#NN)" convention.

Stalemate remediation (use SPARINGLY — only on a genuine stalemate, never as part of a merge). Distinct from the merge decision: a PR can get stuck when AI review bots have posted comments but the user has not responded to them at all — no acknowledgement, no new commits, no replies — and there has been no activity since. Normally that's the user's turn, but they may be blocked: a race condition dropped the GitHub trigger, or they're out of their daily quota (~15/day) of event-triggered agent-routine runs. ONLY when you observe such a real stalemate (unaddressed bot comments AND no user activity since they were posted) you may nudge the review forward instead of merely holding — two equivalent options: (a) add the `review` label to the PR, which fires the user's GitHub-event AI-agent workflow to auto-assess and fix it; or (b) directly find and run the `/review-bot` skill yourself — it is the same skill that workflow uses, so the effect is equivalent and it still works when the label-triggered routine is rate-limited or never fired. Do NOT also merge that PR on the same pass — let the resulting triage land and re-assess on a later pass. Idempotency: do this at most once per stalemate — skip if the `review` label is already present, or if a prior pass already triggered review-bot / added the label and nothing has changed since. This only unblocks a stuck review; it never bypasses the merge gate above.
